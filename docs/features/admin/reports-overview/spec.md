# Reports Overview Specification

## 1. Purpose

Reports Overview is AISLEY's Admin financial analytics and reporting feature for calculating and presenting platform commission/revenue.
`Admin.md` defines:

```text
Core Value:
Calculate platform commission reports,
e.g. how much total did that admin got for the commission.

Expanded Definition:
A financial analytics and reporting module.

It calculates and aggregates revenue
generated by the platform,
specifically tracking commission fees
extracted from user transactions.

It provides temporal filtering:
- daily
- weekly
- monthly

to assess platform financial performance.

System Context:
Involves complex aggregation queries
on Transactions or Orders tables.

May require background job processing
for large financial exports
such as CSV/PDF
without blocking the main thread.
```

This specification defines revenue scope, filtering, breakdowns, exports, permissions, APIs, acceptance criteria, tests, and Open Decisions.
A `flow.md` is included because background export generation has a meaningful asynchronous lifecycle.

## 2. Primary Actor

The primary actor is:

```text
ADMIN
```

Only authenticated and authorized Admins may access platform financial reporting.

## 3. Core Responsibility

Reports Overview owns:

- platform commission/revenue aggregation
- daily/weekly/monthly reporting
- report date filtering
- platform revenue breakdown
- contributing transaction/order references
- summary totals
- trend data
- CSV/PDF export requests when supported
- background export processing
- export status/history
- financial report authorization
- consistency with Admin Dashboard financial metrics
  It does not own:
- payment collection
- subscription charging
- refunds
- chargebacks
- seller payouts
- courier payouts
- logistics payouts
- taxes/VAT
- payment gateway fees
- bookkeeping/general ledger
- forecasting
- budgeting
- manual accounting adjustments
- invoice generation
- seller financial reporting
- courier earnings reporting

## 4. Source-Defined Revenue Model

`app.md` defines:

```text
Admin Commission Flow

Logistics SaaS platform
    base subscription
    + 10 pesos per order

Shipping fee
    default 50 pesos
    this is where logistics get their commission
```

Therefore the source-supported AISLEY revenue model is:

```text
AISLEY Platform Revenue
=
Logistics Base Subscription Revenue
+
Applicable ₱10 Per-Order Platform Fees
```

## 5. Critical Shipping Fee Rule

The default:

```text
₱50 shipping fee
```

belongs to Logistics.
It must not be counted as:

```text
AISLEY platform commission
AISLEY platform revenue
Admin revenue
```

## 6. Revenue Naming

Use clear terminology such as:

```text
Platform Revenue
Platform Commission
```

Do not label the full order value as:

```text
Admin Revenue
```

unless it actually represents AISLEY's earned amount.

## 7. Platform Scope

Reports Overview is:

```text
platform-scoped
```

It is not:

```text
Seller-scoped
Courier-scoped
Logistics internal-profit scoped
Buyer spending scoped
```

## 8. Seller Revenue Boundary

Seller sales and profit are not AISLEY platform revenue.
Seller financial reporting belongs to Seller-facing reports.

## 9. Courier Earnings Boundary

Courier earnings/tips are not AISLEY platform commission.

## 10. Logistics Shipping Boundary

The default shipping fee is Logistics revenue/commission.
Do not add it to AISLEY's platform commission total.

## 11. Buyer Payment Boundary

A Buyer's checkout total is not equivalent to AISLEY revenue.
Only the platform-owned components should be aggregated.

# Revenue Sources

## 12. Logistics Subscription Revenue

AISLEY earns:

```text
base subscription
```

from Logistics under the SaaS model.
Reports Overview should include actual recognized subscription revenue records.

## 13. Approval Is Not Revenue

The Logistics registration flow is:

```text
register
→ Admin approval
→ email
→ sign in
→ subscription
```

Therefore:

```text
Logistics APPROVED
≠
subscription revenue
```

Do not calculate subscription revenue from approved-account counts.

## 14. Subscription Price

The source does not define the base subscription amount.
Therefore:

```text
subscription price = Open Decision / external billing configuration
```

Reports must use actual authoritative subscription charge/payment records rather than inventing a value.

## 15. Per-Order Fee

The source defines:

```text
₱10 per order
```

This is the source-backed per-order platform fee.

## 16. Applicable Order

The source does not define exactly when the ₱10 becomes earned.
Possible interpretations include:

```text
order created
Seller approved
shipped
delivered
paid/settled
```

Do not invent the recognition event.
This is a major Open Decision.

## 17. Revenue Recognition

The source does not define accounting recognition timing.
Reports Overview should consume an authoritative recorded platform-fee transaction/ledger when available.
Recommended:

```text
do not recompute historical revenue
from today's business configuration
if charged values are already stored
```

## 18. Historical Fee Integrity

If the ₱10 fee changes in the future:

```text
historical orders
must preserve the amount actually charged/earned
```

Do not recalculate old records using the new fee.

## 19. Currency

Current source amounts are in:

```text
Philippine pesos (₱ / PHP)
```

Multi-currency behavior is not defined.

## 20. Refunds

The source does not define whether:

```text
refunded order
```

reverses the ₱10 platform fee.
Open Decision.

## 21. Cancellations

The source does not define whether:

```text
cancelled order
```

earns or reverses the per-order fee.
Open Decision.

## 22. Chargebacks

Chargeback treatment is not defined.
Open Decision.

## 23. Subscription Refunds

Subscription refund/credit behavior is not defined.
Open Decision.

## 43. No Double Counting

A source record must contribute to a metric only once according to the authoritative reporting model.

## 44. Subscription Double Counting

Recurring/subscription payment records must not be counted twice because of:

- retry records
- duplicate webhook events
- duplicate joins

## 45. Order Double Counting

Order-fee totals must not multiply because an order joins to:

- multiple items
- multiple shipments
- multiple status-history rows
  Aggregate from an authoritative fee record or carefully scoped query.

# Authorization and Security

## 74. Authentication

```text

```

## 75. Permission

Financial reports may require a dedicated permission.
Possible:

```text

```

Exact permission names are Open.

## 76. CSRF

Export-creation mutations require Sanctum CSRF protection.
Read-only GET report requests do not mutate business state.

## 77. PII Minimization

Reports should avoid exposing unnecessary:

- Buyer address
- Seller payout details
- Courier identity details
- payment credentials
- full phone numbers

## 78. Financial Data Safety

Do not expose:

```text
card numbers
CVV
provider secrets
bank credentials
```

## 79. Export Authorization

Possessing an export ID or file URL does not grant download access.

## 80. Signed Download

If object storage is used, short-lived signed download URLs are recommended.

## 81. Formula Integrity

Do not let the frontend supply:

```text

revenue formula
shipping commission ownership
```

# Acceptance Criteria

## 106. AC-01 — Admin Access

Guests/non-Admins cannot access Reports Overview APIs.

## 107. AC-02 — Permission

Financial report access respects configured Admin permissions.

## 108. AC-03 — Revenue Formula

Total platform revenue uses subscription revenue plus applicable per-order platform fees.

## 109. AC-04 — ₱10 Fee

Per-order revenue uses the authoritative stored/applicable ₱10 platform-fee rule.

## 110. AC-05 — Shipping Exclusion

The default ₱50 shipping fee is excluded from AISLEY platform revenue.

## 111. AC-06 — Logistics Approval

Approved Logistics accounts are not counted as subscription revenue unless an actual authoritative subscription revenue record exists.

## 112. AC-07 — Seller Boundary

Seller gross sales/profit are not reported as AISLEY platform revenue.

## 113. AC-08 — Courier Boundary

Courier earnings/tips are not reported as AISLEY platform revenue.

## 114. AC-09 — Buyer Boundary

Buyer total checkout value is not reported as AISLEY platform revenue.

## 115. AC-10 — Daily

Admin can view a daily platform revenue report.

## 116. AC-11 — Weekly

Admin can view a weekly platform revenue report.

## 117. AC-12 — Monthly

Admin can view a monthly platform revenue report.

## 118. AC-13 — Period Label

Every displayed total clearly identifies its reporting period.

## 119. AC-14 — Currency

Displayed financial amounts identify/use PHP according to current source model.

## 120. AC-15 — Breakdown

Admin can distinguish subscription revenue from per-order platform fees.

## 121. AC-16 — No Double Count

Order/subscription joins do not multiply the same revenue record.

## 122. AC-17 — Historical Integrity

Historical report amounts are not silently recalculated from changed future fee settings when stored charged amounts exist.

## 123. AC-18 — Dashboard Consistency

Dashboard and Reports use the same platform-revenue calculation.

## 124. AC-19 — Pagination

Contributing records are paginated/bounded.

## 125. AC-20 — Export Consistency

Exports use the same filters/calculation as on-screen reports.

## 126. AC-21 — Async Export

Large exports can run without holding the Admin HTTP request open for full generation.

## 127. AC-22 — Export Failure

A failed export is not reported as successfully completed.

## 128. AC-23 — Export Security

Unauthorized Admins cannot download report exports by guessing export IDs/URLs.

## 129. AC-24 — Money Precision

Authoritative money calculations use fixed-decimal arithmetic.

## 130. AC-25 — No GET Mutation

Viewing Reports Overview does not mutate financial business records.

## 131. AC-26 — CSRF

Export creation uses configured Sanctum CSRF protection.

## 132. AC-27 — PII Safety

Reports/exports avoid unnecessary restricted PII.

## 133. AC-28 — Zero State

A period with no revenue displays valid zero/empty state rather than an error.
